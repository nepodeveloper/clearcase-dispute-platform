# PR-04 — Implement dispute eligibility policy

**Batch:** Batch 01 — Engineering foundation

**Scope:** Domain eligibility policies, an authenticated read-only eligibility API, Angular transaction-detail display, tests, and directly related documentation.
**Outcome:** Return a deterministic, customer-safe decision for card purchases, debit orders, and bank charges without creating disputes or initiating financial operations.

## Implement

- Add a pure `IDisputeEligibilityPolicy` abstraction with structured outcomes, reason codes, explanation, policy version, and evaluation timestamp.
- Apply configurable demonstration rules for card windows, effective-dated debit-order windows and review thresholds, and bank-charge review conditions.
- Add `GET /api/v1/transactions/{id}/dispute-eligibility` plus the existing `/v1` compatibility alias. Require authorization and return 404 for missing or inaccessible transactions.
- Display the backend decision, loading and error states on transaction details. Do not add a dispute-submission form.
- Preserve `isDisputable` as a provisional indicator and document its follow-up migration.

## Definition of accepted

- [ ] Card purchase, debit order, and bank-charge policies are independently testable and deterministic.
- [ ] Debit-order effective dates, day boundaries, mandate facts, and the configurable R2,000 internal review threshold are covered.
- [ ] The R2,000 threshold and proposed 60-calendar-day rule are not represented as universal legal requirements.
- [ ] Ownership, authentication, 404 behavior, correlation IDs, and OpenAPI are tested for the read-only API.
- [ ] Angular displays each outcome and the customer-safe explanation, including loading and error states.
- [ ] Existing transaction listing and details contracts remain compatible.

## Non-goals

No dispute persistence/submission, chargeback, reversal, refund, evidence, notifications, Kafka, or background processing.

## Compatibility, safety, and rollback

The eligibility API and UI are additive. Existing routes and payload fields remain unchanged; `isDisputable` remains explicitly provisional until a separate compatible contract change. The policy path has no database schema or financial side effects and can be rolled back by reverting this PR.

## Delivery

- Document demonstration assumptions versus verified production policy.
- Report exact test commands and results.
